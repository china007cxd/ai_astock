# 每日工作日报生成

## 一、模版规则（严格遵循，不得随意变更措辞结构）

日报的每一条工作项，独立成行，必须套用以下两种模版之一：

### 类型 A：OA 需求（2026 年度运维大包内、走 OA 申请的需求）
- 项目：由用户指定（不同项目负责人对应不同小需求项目，需向用户确认）
- 句式：`本项完成OA需求"提出人-需求名称"的XXX工作，达成XXX的目标；目前进度完成XXX%，进度正常。`
- 若进度延期，将 `进度正常` 替换为 `进度滞后`

### 类型 B：运维工单（线上问题处理，涉及改表结构、刷数据、动代码等）
- 项目：固定为 `国科恒泰系统功能服务外包合同`
- 句式：`本项完成运维工单"提出人-工单编号"的XXX工作，达成XXX的目标；目前进度完成XXX%，进度正常。`
- 若进度延期，将 `进度正常` 替换为 `进度滞后`

### 类型 C：协助排查（柔性和非强制，可不提工单）
- 项目：同类型 B，`国科恒泰系统功能服务外包合同`
- 句式：`本项完成"问题简述"的运维工作，达成XXX的目标；目前进度完成XXX%，进度正常。`
- 用于只是协助排查数据、问询系统执行情况等未提工单的场景

详细示例见 [examples.md](examples.md)。

## 二、字段清单（每条工作项必填）

| 字段 | 说明 | 缺失时如何处理 |
|------|------|----------------|
| 类型 | A/B/C | 依据 git 分支名 + 用户描述判断，模糊时询问 |
| 提出人 | OA 需求提出人 或 工单提出人 中文姓名 | **必须问用户**，不能猜测 |
| 需求名称 / 工单编号 | A 用需求名称，B 用工单编号（如 260921071），C 用问题简述 | **必须问用户** |
| 项目 | 类型 A 必须问用户；B/C 自动填 `国科恒泰系统功能服务外包合同` | — |
| 工作内容（XXX工作） | 一句话概括本项做了什么，如"评审""开发""数据修复" | 从 git commit 描述或用户口述提取 |
| 达成目标（XXX的目标） | 本项完成后达成的可交付目标 | 依据 commit 内容推断并向用户确认 |
| 进度百分比 | 0-100 的整数 | **必须问用户**，默认建议 100 |
| 进度状态 | 正常 / 滞后 | 默认"进度正常"，用户可改 |

## 三、标准工作流

### 步骤 1：确定日期范围
默认"今天"。若用户指定日期（如"昨天""9 月 20 日"）则按用户指定。计算 git 命令的时间窗口。

### 步骤 2：拉取当日 git 提交
执行（Windows cmd 兼容）：
```
git -C <workspace> log --all --since="YYYY-MM-DD 00:00" --until="YYYY-MM-DD 23:59" --author="<git user.name>" --pretty=format:"%h|%ad|%d|%s" --date=short
```
若用户希望包含未提交或 stash 的内容，追加询问。

### 步骤 3：按分支聚合分类
- 分支名含 `feature/OA-` `feature/需求` 等 → 归为类型 A
- 分支名含 `hotfix/` `fix/工单` 或 commit 前缀 `fix(...)` 且用户明确说运维 → 归为类型 B
- 其他 fix/排查类且无工单号 → 归为类型 C
- **不确定时**必须询问用户："这条提交 [commit msg] 是走 OA 的需求，还是运维工单？提出人是谁？"

同一天的多个 commit 若属于同一个需求/工单，应合并为**一条**日报条目；跨需求/工单则拆成多条。

### 步骤 4：逐项补齐缺失字段
用 AskUserQuestion 一次性把当天所有条目的缺失字段合并询问（每条最多 3-4 个问题），避免逐字段往返。对每个条目：
- 从 commit message 提炼"工作内容"与"达成目标"的草稿，展示给用户确认或修改
- 询问 提出人、需求名称/工单编号、项目（类型 A 时）、进度%、进度状态

### 步骤 5：生成最终日报文本
按类型模版逐条输出，行间空一行，方便复制粘贴。若用户希望同时给出"项目"标注，在每条前面加一行 `[项目：XXX]` 辅助注释（正式提交时用户可自行删除）。

## 四、Commit message 建议规范（可选，方便后续自动化）

为减少每次询问提出人/工单号的成本，建议用户按以下格式提交，脚本可自动解析：
```
feat(OA#董涛-SAAS系统功能迭代更新): 增加下载接口
fix(工单#高薪淇-260921071): 修复爱康台账锁定数量
```
解析规则：正则 `(feat|fix|refactor)\((OA|工单)#([^-]+)-([^)]+)\):\s*(.+)`
- 组 2 = 类型（OA→A / 工单→B）
- 组 3 = 提出人
- 组 4 = 需求名称/工单编号
- 组 5 = 工作内容草稿

若 commit 未遵循此格式，回退到"询问用户"路径。

## 五、注意事项

1. **不擅自伪造**提出人姓名、工单编号、需求名称——必须来自用户或 git commit 中显式声明的字符串
2. **进度百分比**不能默认 100 直接输出，需要用户确认；但对于当日已 merge 到 develop/main 的完成型工作，可以先建议 100% 并请用户确认
3. **同一需求/工单多 commit 合并**：日报按条目组织，不按 commit 组织
4. **类型 B 项目名固定不变**：`国科恒泰系统功能服务外包合同`（注意是"恒泰"不是"恒泰科技"，一字不差）
5. **输出语言**：中文；标点使用全角引号 `"…"` 与模版示例保持一致
6. **联系产品经理兜底**：若用户明确表示不清楚某需求是否走 OA，回复"建议联系产品经理或对应开发负责人确认"，不要臆断

## 六、快速示例

输入（用户提供）：
> 今天写了三方调拨单导出优化那个 OA，董涛提的，评审 + 开发都做完了，进度 100%；另外处理了个高薪淇的工单 260921071，刷台账锁定数据，也 100%。

输出：
```
1. [项目：董涛-SAAS系统功能迭代更新]
本项完成OA需求"董涛-SAAS系统功能迭代更新"评审工作，达成可交付开发设计及编码的目标；目前进度完成100%，进度正常。

2. [项目：董涛-SAAS系统功能迭代更新]
本项完成OA需求"董涛-SAAS系统功能迭代更新"开发工作，达成三方调拨单导出明细查询逻辑优化的目标；目前进度完成100%，进度正常。

3. [项目：国科恒泰系统功能服务外包合同]
本项完成运维工单"高薪淇-260921071"的处理爱康历史寄售台账存在锁定数量数据的工作，达成将爱康经销商有问题的台账锁定数据修复的目标；目前进度完成100%，进度正常。
```
